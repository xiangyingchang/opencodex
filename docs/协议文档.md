# Provider Split Bridge 协议

> 状态：实施中（Phase 0 基线/能力探针、Phase 1 回滚快照和 Phase 2 Provider Split Map 已完成；Phase 3 已实现隔离的 HTTP/SSE handler 与测试，但尚未接入生产 server、launchd 或 Codex 配置，数据面尚未切换）。本文件先于运行时代码，作为目标行为和回滚契约。

## 1. 当前行为

当前 OpenCodex 2.10.2 的 Codex loopback 注入把内置 `openai` provider 的入口指向：

```toml
openai_base_url = "http://127.0.0.1:10100/v1"
```

因此官方 GPT 与第三方模型都会先进入同一个 OpenCodex 进程。当前模型目录可以区分官方裸模型和第三方 `provider/model`，但这只是网关内部路由，不是故障域隔离。

在 Provider Split Bridge 正式启用前，以上行为保持不变。

## 2. 目标拓扑

Codex App/CLI/TUI 继续读取同一份 `$CODEX_HOME` 配置和 catalog，但入口改为独立的本地 Split Bridge：

```text
Codex
  -> http://127.0.0.1:10101/v1
       ├─ official-native / official-native-account
       │    -> ChatGPT/Codex official upstream
       └─ third-party-gateway
            -> http://127.0.0.1:10100/v1
                 -> configured third-party provider
```

`10101` 与现有 `10100` 必须是独立进程、独立 launchd label、独立健康状态和独立资源预算。10101 的官方分支不得先检查、等待或排队于 10100。

## 3. 通道分类

### 3.1 官方原生 Codex

```text
gpt-5.6-luna
<selector>/gpt-5.6-luna
```

这些条目使用 Codex/ChatGPT 原生凭据和 official direct upstream，不能进入第三方网关。

### 3.2 OpenAI API-key

```text
openai-apikey/gpt-5.6-luna
```

API-key 是独立凭据通道，不能仅按 `gpt-*` 前缀归类。实施时必须明确它是：

- `official-api-key-direct`：经独立 OpenAI API direct branch；或
- `gateway-required`：由 OpenCodex 10100 管理其 key。

在该决策完成前，不得把 API-key 条目误称为原生 Codex 直连。

### 3.3 第三方模型

```text
ark-coding/deepseek-v4-flash
deepseek/deepseek-v4-flash
```

第三方模型必须进入 10100。10100 不健康时返回稳定的 `503 gateway_unavailable`，不得回退到官方 OpenAI。

### 3.4 未知模型

未知、空、格式冲突或 catalog generation 不一致的模型必须 fail-closed，不得落入默认 provider，不得发送到任一上游。

## 4. Model picker 契约

官方和第三方条目继续作为 `visibility = "list"` 的 Codex catalog entries 同时保留。网关不健康时不删除第三方条目，避免 Codex App 选择器随网关状态闪烁；用户选择第三方条目后，由运行时返回 `gateway_unavailable`。

`ocx sync` 负责重建 catalog 并使 `models_cache.json` 失效。catalog 只表达可选择的模型身份，不代表第三方网关当前 ready。

模型选择器显示成功与请求 transport 成功是两个验收项：HTTP/SSE、WebSocket/app-server、Images、compact、search、Live/Realtime 必须分别验证；没有测试的 surface 不宣称支持。

## 5. Header 与凭据边界

官方分支可以转发经过 allowlist 的 Codex/OpenAI auth/session headers。

第三方分支必须：

- 删除 OpenAI bearer、`chatgpt-account-id`、Codex session/account headers；
- 只添加由 bridge 配置的 `x-opencodex-bridge-admission` service admission token；
- 不在日志、审计记录、错误正文或测试 fixture 中保存 token/key；
- 第三方错误不得改变官方凭据、Codex `openai_base_url` 或官方 catalog。

## 6. 故障语义

| 条件 | 官方 native GPT | 第三方模型 |
| --- | --- | --- |
| 10100 健康 | 直达 official upstream | 进入 10100 |
| 10100 干净停止 | 不变 | `503 gateway_unavailable` |
| 10100 崩溃/SIGKILL | 不变 | `503` 或短熔断 |
| 第三方 401/429/5xx/timeout | 不变 | 仅第三方失败 |
| 官方 upstream 故障 | 官方失败 | 不得借道官方 |
| 10101 自身崩溃 | 有短暂 bridge 故障窗口 | 同样不可用；由独立 launchd 自动恢复 |

本协议承诺的是“10100/第三方故障不传播到官方路径”，不是机器断网、操作系统耗尽资源、凭据失效或 10101 自身故障时的绝对可用性。

## 7. 生命周期

目标服务：

```text
com.opencodex.proxy         -> 10100 third-party gateway
com.opencodex.split-bridge  -> 10101 official direct + gateway forward
```

10101 启动不要求 10100 已启动；10100 启动、停止或重启不应重启 10101。建议 `ocx stop` 在 split mode 下停止 10100 但保留 10101，让 GPT 继续可用；`ocx restore` 才退出 split mode 并恢复 native Codex。正式启用前必须通过 CLI 行为测试锁定该语义。

## 8. 写入、审计和回滚

所有 Codex 写入必须通过现有 `inject.ts`、journal、generation check 和 atomic write。不得手工覆盖用户-owned `openai_base_url`。

正式切换前备份：

```text
~/.codex/config.toml
~/.codex/opencodex.config.toml
~/.codex/opencodex-catalog.json
~/.codex/models_cache.json
~/.opencodex/config.json
~/Library/LaunchAgents/com.opencodex.proxy.plist
```

快照存放在用户目录下的权限受限 run 目录，日志只记录路径、权限和 SHA-256。失败时先卸载 10101，再使用 journal/`ocx restore` 恢复；必要时按 manifest 恢复快照。禁止删除用户文件、`git reset --hard`、`git checkout --` 或 force-push。
