# Provider Split Bridge 协议

> 状态：实施中且 activation-gated（Provider Split Map、隔离 HTTP/SSE handler、catalog、三态 routing state、Codex injection/restore 和 foreground/LaunchAgent 接线已落地；native path、HTTP fallback、官方 body normalization、restore write lock、gateway admission、readiness 和完整 LaunchAgent 生命周期必须通过本文件的 fake-upstream 验收后才可激活）。本文件是目标行为和回滚契约，不是 completion 成功证明。

## 1. 当前行为

当前 OpenCodex 2.10.2 的 Codex loopback 注入把内置 `openai` provider 的入口指向：

```toml
openai_base_url = "http://127.0.0.1:10100/v1"
```

因此官方 GPT 与第三方模型都会先进入同一个 OpenCodex 进程。当前模型目录可以区分官方裸模型和第三方 `provider/model`，但这只是网关内部路由，不是故障域隔离。

在 Provider Split Bridge 正式启用前，以上行为保持不变。

## 2. 目标拓扑

Codex App/CLI/TUI 继续读取同一份 `$CODEX_HOME` 配置和 catalog，但入口改为独立的本地 Split Bridge：

```text
Codex
  -> http://127.0.0.1:10101/v1
       ├─ official-native
       │    -> ChatGPT/Codex official upstream
       ├─ official-native-account
       │    -> http://127.0.0.1:10100/v1 exact-account route
       └─ third-party-gateway
            -> http://127.0.0.1:10100/v1
                 -> configured third-party provider
```

`10101` 与现有 `10100` 必须是独立进程、独立 launchd label、独立健康状态和独立资源预算。裸官方分支不得先检查、等待或排队于 10100；账户限定分支是有意保留 selector 并交给 10100 的精确凭据路由例外。

### 2.1 HTTP endpoint 与 fallback contract

Split Bridge 的入站路径是 Codex 的 `/v1/responses` 和 `/v1/responses/compact`，但两个上游平面不共享路径拼接规则：

- native base `https://chatgpt.com/backend-api/codex` 映射到 `/backend-api/codex/responses` 和 `/backend-api/codex/responses/compact`；入站 `/v1` 不是 native upstream 的路径前缀；
- gateway base `http://127.0.0.1:10100/v1` 保留 `/v1/responses` 和 `/v1/responses/compact` 语义；
- query string 必须保留，base path 只能是经过校验的固定 prefix，不得由入站 URL 选择 origin 或穿越到其他 path。

第一阶段不宣称 10101 原生支持 Responses WebSocket。对 `/v1/responses` 的 WebSocket upgrade 返回 JSON `426`，`error.type` 和 `error.code` 均为 `upgrade_required`，且不得调用任何 upstream；Codex 随后必须使用同一入口的 HTTP POST fallback。fallback 没有 fake-upstream 协议证据前，split 不可激活。

## 2.2 Codex routing mode 与恢复边界

配置字段 `codexRoutingMode` 只接受：

- `legacy-local`：兼容当前 10100 注入行为；缺省值保持此模式；
- `split`：目标入口为 `http://127.0.0.1:10101/v1`。

`native`、`split`、`legacy-local` 是对当前 `config.toml` 的观测状态，不等同于用户意图：

- 无 bridge marker 的 `openai_base_url` 永远视为用户-owned，不得因为 URL 恰好指向 10101 就删除；
- marker 与预期 URL 不匹配时 fail-closed；
- 没有 legacy ownership proof 时不得盲目覆盖或恢复 10100 provider table；
- restore 只能删除已证明由 bridge 写入的 routing keys，用户 model、无关 TOML table 和自定义 endpoint 必须保留。

## 3. 通道分类

### 3.1 官方原生 Codex

```text
gpt-5.6-luna
<selector>/gpt-5.6-luna
```

裸条目使用 Codex/ChatGPT 原生凭据和 official direct upstream，不能进入第三方网关。账户限定条目
必须保留完整 selector 进入 10100 的 exact-account 路由，由已有认证生命周期解析映射凭据；10101
不得把调用方 Authorization 或 `chatgpt-account-id` 直接当作该账户的凭据。selector 缺失、过期、
暂停、需要重新认证或 10100 不可用时必须 fail-closed。

### 3.2 OpenAI API-key

```text
openai-apikey/gpt-5.6-luna
```

API-key 是独立凭据通道，不能仅按 `gpt-*` 前缀归类。本阶段固定为
`gateway-required`：由 OpenCodex 10100 管理其 key。10101 没有独立的 OpenAI API direct
branch，因此不得把 API-key 条目误称为 ChatGPT/Codex 原生直连。

### 3.3 第三方模型

```text
ark-coding/deepseek-v4-flash
deepseek/deepseek-v4-flash
```

第三方模型必须进入 10100。10100 不健康时返回稳定的 `503 gateway_unavailable`，不得回退到官方 OpenAI。

### 3.4 未知模型

未知、空、格式冲突或 catalog generation 不一致的模型必须 fail-closed，不得落入默认 provider，不得发送到任一上游。

## 4. Model picker 契约

官方和第三方条目继续作为 `visibility = "list"` 的 Codex catalog entries 同时保留。网关不健康时不删除第三方条目，避免 Codex App 选择器随网关状态闪烁；用户选择第三方条目后，由运行时返回 `gateway_unavailable`。

`ocx sync` 负责重建 catalog 并使 `models_cache.json` 失效。catalog 只表达可选择的模型身份，不代表第三方网关当前 ready。

`ocx status --json` 的 `splitBridge` 诊断固定包含 `splitBridgeRunning`、`splitBridgePort`、`officialPath`、`thirdPartyPath = gateway`、`gatewayReachable`、`catalogGeneration` 和 `routingDependency`。`split` 模式下 `officialPath = direct`、`routingDependency = split-bridge-not-gateway`；缺省 `legacy-local` 模式下 `officialPath = legacy-local`、`routingDependency = legacy-local`，Split Bridge 专用 10100/10101 probes 标记为 inactive，但 `gatewayReachable` 仍复用当前 legacy proxy health。bridge down 与 gateway down 必须分别报告；gateway down 不得改变官方 path 或 catalog generation。

`ready` 不是 `/healthz` 的别名。split readiness 还必须同时证明 native route table、HTTP fallback capability、官方 transport contract、catalog generation、bridge-owned routing injection、gateway admission 配置和独立 LaunchAgent 生命周期；缺一项应报告稳定的 `bridge-unavailable`、`gateway-unavailable`、`configuration-invalid` 或 `transport-unverified`，而不是乐观 ready。

模型选择器显示成功与请求 transport 成功是两个验收项：HTTP/SSE、WebSocket/app-server、Images、compact、search、Live/Realtime 必须分别验证；没有测试的 surface 不宣称支持。

账户受限的 native 模型 selector 只在已确认的 main/Pool roster 包含该精确 slug，且缓存条目的
credential generation 仍与当前账户凭据一致时才可见。main identity 必须绑定 account id 和
access-token fingerprint，并在读取时验证 JWT liveness；凭据被替换、删除、过期或 roster 无法确认时，
同步 catalog、`/v1/models` 和 management selector 在投影前都必须重新验证 snapshot 的 credential identity；若 discovery 等待期间 credential 被替换、删除或过期，整份 entitlement evidence 视为 stale 并对 account-gated native rows fail-closed，但不影响非 gated routed/native rows。Direct caller 的 roster 只用于它自己的请求，不得成为全局 selector availability 证据。

## 5. Header 与凭据边界

官方分支可以转发经过 allowlist 的 Codex/OpenAI auth/session headers。

第三方分支必须：

- 删除 OpenAI bearer、`chatgpt-account-id`、Codex session/account headers；
- 只添加由 bridge 配置的 `x-opencodex-bridge-admission` service admission token；
- 10100 在 split admission mode 下必须从 owner-only token file 读取同一 secret，并用 constant-time comparison 验证该 header；缺失、错误或空白 token 返回稳定 `401`。loopback data-plane bypass 不能绕过这项专用检查；legacy-local 未启用该 mode 时仍保持原有 loopback 兼容语义；
- 不在日志、审计记录、错误正文或测试 fixture 中保存 token/key；
- 第三方错误不得改变官方凭据、Codex `openai_base_url` 或官方 catalog。

## 6. 故障语义

| 条件 | 官方 native GPT | 第三方模型 |
| --- | --- | --- |
| 10100 健康 | 直达 official upstream | 进入 10100 |
| 10100 干净停止 | 不变 | `503 gateway_unavailable` |
| 10100 崩溃/SIGKILL | 不变 | `503` 或短熔断 |
| 第三方 401/429/5xx/timeout | 不变 | 仅第三方失败 |
| 官方 upstream 故障 | 官方失败 | 不得借道官方 |
| 10101 自身崩溃 | 有短暂 bridge 故障窗口 | 同样不可用；由独立 launchd 自动恢复 |

本协议承诺的是“10100/第三方故障不传播到官方路径”，不是机器断网、操作系统耗尽资源、凭据失效或 10101 自身故障时的绝对可用性。

### 6.1 请求级 upstream retry budget（Phase 1.1）

- `fetchWithTransientRetry` 的 `opts.attempts` 是单个逻辑请求的全局发送次数上限（包含首次发送），由 connection reset 与 transient 5xx 共同消耗；故障类型切换不得重新装载预算。cancel/deadline 优先于 backoff 和下一次发送，retry 前必须对未读 response body 发起并 bounded-await cancel（cancel 永不 settle 时由有限 cleanup 预算放行下一次发送）。仅 pre-stream 失败允许重试；mid-stream 已开始输出后不得 replay。若 reset 层和外层 5xx 层都产生 `UpstreamRetryEvidenceError`，最终错误必须扁平合并全部 `transientStatuses`、使用 OR 语义合并 `resetSeen`，并把最底层非 evidence rejection 作为 `cause`，不得让 evidence 嵌套遮蔽 transport `code`；即使最后一次允许发送仍以 connection reset 失败，也必须返回 evidence wrapper，不得让 raw terminal error 丢失已累计的 `resetSeen` 或 transport attribution。

- 10101 的 `official-native` split-bridge relay 必须复用同一有界的 pre-stream `fetchWithResetRetry` contract：重放使用已序列化的请求 body，并通过 `applyUpstreamRecoveryInit` 让 reset retry 使用 `Connection: close` 与 `keepalive: false`；一旦 `Response` 已建立或 body 已开始输出，不得 replay。10101 的 gateway/account/search/image 分支保持一次 upstream 调用语义，不在 10100 已有策略外再套一层 retry。
- `official-native` 的 SSE upstream request 必须强制 `Accept-Encoding: identity`，避免 Bun 在 gzip/zstd 响应体中途截断时进入压缩解码层并把 `ZlibError` 传给 Codex；client-facing response 同时不得转发 `content-encoding`、`content-length` 或其他 hop-by-hop framing 头。
- 每次 native attempt 都必须传递同一个、与 `request.signal` 联动的 abort signal；请求取消优先于 backoff 和下一次发送。native response 不得为 admission 计数而全量 buffer：lease 必须持续到 response body EOF、下游 cancel 或上游 error，并在 fetch/Response 构造失败时 exactly-once release；所有 body 失败路径都必须同时取消上游 reader，且不得在 stream 已开始后重试。
- 如果 `official-native` 已经建立 200 SSE response 后 reader 抛错，bridge 只能保留已收到的字节，追加一个有界的 `response.failed` 与 `data: [DONE]` 尾帧后关闭；这只是可解析的失败表示，不是请求成功，也不构成 replay。失败尾帧只能使用固定的安全错误类别/transport code，不得序列化原始 `err.message` 或 `String(err)`；若 response body 在没有合法 Responses terminal event 的情况下 clean EOF，也必须使用同一失败表示。底层错误只记录非敏感的错误类别/transport code，不记录 body、凭据或完整 URL；客户端主动 cancel 不得被误记为 upstream body failure。

实施状态：Phase 1.1 已实现并补完 evidence 扁平化；混合 reset/transient 回归、transport attribution、abort/backoff 和 body cancel 测试通过。

### 6.2 SSE relay queue/backpressure budget（Phase 1.2）

`relaySseEagerBounded` 使用 byte-length queuing strategy：`controller.desiredSize` 与 `maxQueueBytes` 的差值表达真实留在下游 `ReadableStream` 内部队列的字节数；pending reader 直达时 desiredSize 不下降，producer 在差值达到 cap 时停止读取，并将 oversized chunk 切成不大于剩余 cap 的 slices。`maxQueueBytes` 必须是有限数值，非有限配置回退默认值，有限值至少规范化为 1。`pull()` 只负责唤醒 producer，不假设一次 pull 等于一个 chunk 消费，避免多 chunk 队列下错误扣账。cancel/error 由 stream 清空内部队列后释放等待状态；正常 close 仍允许已排队尾部被消费。

`relaySseWithBlockRewrite` 使用默认 HWM=1 的 JS stream chunk strategy：在单次 pull 内，pending reader 直达的第一块不计费，后续真正进入内部队列的输出 chunk 记录各自 byte size；下一次 pull 只会在该内部 chunk 队列已清空后释放这一批 retained bytes，cancel/error 则释放全部剩余输出。这样不假设一次 pull 等于一个 chunk，同时避免 EOF close 后没有后续 pull 导致预算泄漏。`desiredSize` 只用于区分直达与入队，不等同于已证明 Bun 原生 HTTP Response sink 的网络 backpressure；该 runtime 事实仍需独立基准验证。

实施状态：Phase 1.2 已完成；实现、三文件离线回归、独立高风险 review 均通过。review 仅留下后续增强建议：直接暴露 upstream `reader.read()` 计数/精确边界的测试，以及 queued-output 后发生 error 和 disposer exactly-once race 的专项测试；不切换默认 eager policy，不宣称 Bun 原生 Response sink 已有网络背压。

### 6.3 Readiness failed 恢复状态机（Phase 1.3）

readiness 继续对外只暴露固定的 `pending | ready | failed` 三态；`/healthz` 仍只表示进程存活，`/readyz` 仍在 `pending`/`failed` 时返回 `503 + Retry-After: 1`，不得把内部故障原因、provider 输出、配置路径、账号或凭据写入响应。恢复是显式、有限、可取消的状态机，不是永久后台重试：

- 初始状态为 `pending`；只有同步结果 `ok=true` 且没有非空 `warning` 才允许 `pending -> ready`。
- 失败同步只能把 `pending -> failed`；`ready`/`failed` 的旧终态不会被普通 `markReady`/`markFailed` 互相覆盖。需要重试时必须先调用唯一的 `beginRecovery()`，仅允许 `failed -> pending`，之后再由成功同步进入 `ready`；不得直接 `failed -> ready`。同一个 gate 的 `runStartupReadinessSync` 具备单 flight 语义：并发调用 join 已存在的 sync，不得重复调用 provider；每轮带有 gate-local generation，迟到的旧 completion 不得覆盖新一轮状态。
- 每轮 startup/recovery sync 的 attempts 是单个逻辑同步的总尝试数（包含首次尝试），默认最多 3 次，默认 backoff 为 `100ms`、`250ms`；只对明确标记 `retryable=true` 的结果，以及未分类的 throw/null 暂时故障重试。`ok=false` 或 `warning` 未标记为可重试的结果按永久配置/应用失败处理，耗尽预算后 fail closed。
- 每次 backoff 和每次同步结果回收都必须检查同一个 `AbortSignal`；shutdown 触发 abort 后不得 sleep、不得再发起下一次 sync、不得把迟到的成功结果写成 `ready`。恢复没有无限 timer，也不因失败自动创建新的进程。
- 每次恢复最多一个 in-flight sync；gate 本身对并发调用复用既有 flight、拒绝重复 provider 执行并保护 generation，调用方仍应串行触发 recovery。每个 server 的 gate 仍为私有实例，不能用模块全局状态污染另一个 listener；`/readyz` 的 body schema 和 sanitization 契约不变。

实施状态：Phase 1.3 先以 fake sync 验证 `failed -> pending -> ready`、transient bounded retry、永久失败不重试、abort 不继续发送/睡眠和 per-server isolation；不得使用真实 provider、不得重启服务、不得修改 LaunchAgent。若完整套件仍命中 GUI 缺少 `react`/`react/jsx-dev-runtime` 的已知失败基线，必须原样报告，不得写成全量通过。

### 6.4 Shutdown absolute deadline（Phase 1.4）

`drainAndShutdown(server, timeoutMs)` 在入口记录一次绝对截止时间 `deadline = now + max(0, timeoutMs)`；该 deadline 覆盖整个 shutdown 链路，而不是每个阶段重新获得一段 timeout。覆盖范围依次包括 temporary drain、active turn drain、background shell drain、response/replay state flush、storage scheduler/job abort、storage worker join、public listener stop 和 native startup lifecycle release。

- 每个可能等待的阶段只能使用 `deadline - now` 的剩余预算；remaining 为 0 时不得开启新的阻塞等待。hung promise 不得阻塞后续 best-effort cleanup 或让 `drainAndShutdown` 超过总 deadline 返回。
- active turn 到达截止时间后必须 abort/release；background shell、state flush、storage abort/join、listener stop 和 lifecycle release 均只尝试一次。listener stop 内的 public listener、loopback listener、overlay、background lifecycle 和 native lifecycle release 也必须是彼此独立的 best-effort 子步骤；其中一个 hung/rejected 不能跳过后续子步骤。阶段超时或失败必须记录 bounded、secret-free warning；rejected phase 仍不得覆盖其他阶段的 cleanup，且全部 phase 处理完后 `drainAndShutdown` 必须对失败结果 fail-closed reject，禁止调用方把未完成的 shutdown 当作成功并继续 replacement bind。
- listener stop 与 startup lifecycle release 即使 deadline 已到也要 best-effort 发起，但不得无限 await；迟到 promise 不得重新打开 admission、恢复 scheduler 或改变 shutdown 终态。既有 exactly-once stop/release 语义必须保持。
- `timeoutMs` 为负数按 0 处理；不得用嵌套的相对 timeout 把总等待时间放大。正常路径在截止时间内仍等待必要的 flush/join；超时路径 fail closed，进程调用方负责最终 exit，不执行新的 provider 请求。
- 测试必须使用 localhost/fake hooks 或永不完成的 promise，证明每一阶段共享同一个 absolute deadline、hung phase 不拖过 deadline、后续 cleanup 仍被尝试，并覆盖 timeout=0、阶段失败、重复 shutdown 和 listener stop/release exactly once。不得重启真实服务、修改 LaunchAgent 或调用真实 provider。

实施状态：Phase 1.4 的实现与 focused 验收完成后回写；完整测试若继续命中既有 GUI 依赖失败，必须与本阶段 shutdown 结果分开报告。

### 6.5 Split admission 与 10100/10101 资源隔离（Phase 1.5）

- split mode 下按**逻辑流量域**隔离 admission：`official-native` 与 `official-native-account` 归入 `native`；`third-party-gateway` 与 `official-api-key` 归入 `gateway`。不能因为 account traffic 物理上转发到 10100 就和 third-party 共用一个 gate。
- 10101 split bridge 和 10100 gateway 各自维护 native/gateway 两个独立 gate；legacy-local 继续使用既有 `MAX_ACTIVE_TURNS`，不得被 split gate 改写。
- 默认每个 split 域最多 128 个 active turn（两域合计保持约 256）；测试或本地 fake listener 可以通过非持久化 options 注入更小的正整数。非法、零、负数、非安全整数必须 fail closed。
- admission lease 必须覆盖完整上游 response stream：fetch 成功但 body 尚未 EOF 时不能释放；下游 cancel、上游 EOF 或 error、fetch/Response 构造失败都必须 exactly-once release。不得为计数而全量 buffer SSE。
- 域容量耗尽必须在调用上游前返回 JSON `503`、稳定 `server_busy` code 和 `Retry-After: 1`；不得跨 native/gateway fallback，不得把请求排队到无界内存。
- 10100 的 branch 识别只能接受配置的 split bridge admission token；有 token 且带非空 account-selector header 的请求归 native，其余受信 split 请求归 gateway；无效/缺失 token 不能获得任一 split gate。
- `/healthz`/metrics 只可暴露 active/peak/admitted/rejected 等非敏感计数；不得回显 token、Authorization 或上游 body。此阶段只承诺 admission 隔离，不宣称已完成独立进程、retry budget 或 memory budget。
- 验收必须使用 localhost/fake fetch：填满 gateway 后 native 仍至少可成功一个请求；释放/取消后容量可回收；超限请求无 upstream call、两个域 metrics 独立；不得调用真实 provider、不得重启 10100/10101、不得修改 LaunchAgent。

实施状态：Phase 1.5 已实现：10101 split bridge 与 split mode 下的 10100 gateway 各自按 native/gateway 建立独立 bounded gate；handler 级 fake-fetch 验证容量隔离、503/Retry-After、EOF/error/cancel exactly-once release 和非敏感 metrics；10100 的 trusted-token branch 选择与请求路径接线已覆盖。验收未启动真实 10100/10101、未调用真实 provider、未修改 LaunchAgent。

## 7. 生命周期

目标服务：

```text
com.opencodex.proxy         -> 10100 third-party gateway
com.opencodex.split-bridge  -> 10101 official direct + gateway forward
```

  10101 启动不要求 10100 已启动；10100 启动、停止或重启不应重启 10101。裸官方请求不依赖 10100，账户限定和第三方请求在 10100 不可用时分别返回 exact-account/gateway failure。Split Bridge 必须有可测试的 `install`、`load`、`status`、`stop`、`uninstall` 和 `repair` 生命周期；仅有 foreground `start` 或只生成 plist 时，status 必须明确报告 lifecycle unavailable，不得把已注入 10101 的 Codex 宣称为 ready。建议 `ocx stop` 在 split mode 下停止 10100 但保留 10101，让裸 GPT 继续可用；`ocx restore` 才退出 split mode 并恢复 native Codex。正式启用前必须通过 CLI 行为测试锁定该语义。

## 8. 写入、审计和回滚

所有 Codex 写入必须通过现有 `inject.ts`、journal、generation check、同一个按 canonical `CODEX_HOME` 建立的 write lock 和 atomic write。Injection 与 restore 都必须在锁内重新读取 config/profile、ownership 和 generation；不得用 stale snapshot 覆盖新 injection，也不得手工覆盖用户-owned `openai_base_url`。不可 await 的强制退出路径只能 fail-closed 并留下可操作告警。

### 8.1 Native history rollout residue 的 bounded scan 契约

restore 在首次建立 coordination row 前检查 history database 和 backup manifest 引用的 rollout。rollout 文件的总大小本身不是拒绝理由；检查必须使用 bounded-memory 的 UTF-8 分块/流式 JSONL 扫描，不得把整个 rollout 读入内存。合法换行分隔的超大文件仍可被判定为干净，但扫描必须同时覆盖首个和最后一个 `session_meta`，并在观察前后确认原始引用路径（包括 symlink 身份）、resolved target 的完整文件 identity（含 inode、size、mtime/ctime）及其已解析路径没有变化。

单条 JSONL record 仍有独立的有界长度；超长或无界 record、malformed JSON、缺失或无效的 `session_meta`、provider 混合/不一致、文件变化以及路径解析/替换异常，都必须 fail-closed（返回既有的 `indeterminate` 或 residue 分类），不得为了接受大文件而放宽这些安全条件。`openai` 以及 Codex 已知的外部 `custom` provider，在整个 rollout 的 `session_meta` provider 一致、线程元数据有效且没有 `opencodex` 时，不单独证明 OpenCodex residue；`openai`/`custom` 等 provider 混合仍拒绝 seed，未识别 provider 仍返回 `indeterminate`。

正式切换前备份：

```text
~/.codex/config.toml
~/.codex/opencodex.config.toml
~/.codex/opencodex-catalog.json
~/.codex/models_cache.json
~/.opencodex/config.json
~/Library/LaunchAgents/com.opencodex.proxy.plist
```

快照存放在用户目录下的权限受限 run 目录，日志只记录路径、权限和 SHA-256。失败时先卸载 10101，再使用 journal/`ocx restore` 恢复；必要时按 manifest 恢复快照。禁止删除用户文件、`git reset --hard`、`git checkout --` 或 force-push。
